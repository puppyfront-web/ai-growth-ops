# 真实平台逐账号验收 Runbook

状态：待执行（等待用户提供低风险测试账号与书面批准）
适用：`spec/11` 实施结果清单中"真实平台发送/回复"与"小红书真实账号主动获客"两项验收。
原则：遵守 `AGENTS.md` 第 9/10 节——未经书面批准不得向真实平台发送；无外部证据不得把能力标为已验证。

## 0. 为什么需要这个流程

自动化测试（单元/集成/E2E）只证明代码路径正确，不证明平台真实可用。按平台能力诚实原则，`verified` 状态必须由"授权账号完成真实动作 + 保留外部 ID/时间/截图/日志"支撑。本 Runbook 把验收动作收敛为最小集合：每个能力一次真实动作。

> 快速自查：`pnpm acceptance:readiness` 对以上条件做只读检查（不发送任何内容），
> 批准单模板见 `docs/delivery/acceptance-evidence/APPROVAL-TEMPLATE.md`。

## 2. 书面批准模板（复制填写后存档到本目录）

```text
真实平台验收批准单
日期：____
批准人（业务负责人）：____（姓名/角色）
执行人：____

批准执行的动作用真实账号各完成一次，对象均为测试数据：
1. 抖音测试账号「____」对一条测试评论/私信发送一条真实回复；
2. 将一个测试客户真实写入飞书多维表格「____」；
3. （可选）小红书测试账号「____」执行一次低量关键词采集（≤3 视频）。

不批准的范围：主账号发布、批量发送、真实客户数据写入、任何未列出的动作。
撤销条件：出现风控提示/验证码即停止，剩余动作作废。
```

## 3. 验收步骤与证据要求

### 3.1 抖音真实回复（关闭"真实平台发送/回复"项）

1. 扫码登录测试账号，确认健康检查通过。
2. 同步一条测试评论/私信（评论私信 → 同步）。
3. 在审核队列对该互动执行一次回复（人工确认后发送）。
4. 记录证据：

| 证据 | 内容 |
| --- | --- |
| 外部回复 ID | `reply_attempts.external_reply_id` |
| 发送时间 | `reply_attempts.created_at` |
| 平台截图 | 评论区显示该回复的截图 |
| 日志 | API/Worker 日志片段（无密钥） |
| 失败路径 | 若失败：错误码 + 恢复指引是否清晰 |

5. 验收通过后：能力矩阵 `douyin.reply` 由 `beta` → `verified`（`packages/shared/src/platform-capabilities.ts`），同步更新 `docs/delivery/crm-release-status.md` 与本文件状态，并补充 `tests/unit/shared/platform-capabilities.test.ts` 断言。

### 3.2 飞书真实写入（关闭 P0 交付记录中的阻断项）

1. 配置飞书多维表格（集成 → 同步与推送）。
2. 创建一个测试客户，点击"同步飞书"。
3. 在飞书表格中核对新增行与字段。
4. 记录证据：`LeadExternalMapping.externalId`、`externalUrl`、同步时间、表格截图、失败重试路径说明。
5. 通过后更新 `crm-release-status.md` 的"真实平台"一节。

### 3.3 小红书低量采集（关闭"小红书真实账号主动获客验收"项）

1. 扫码登录小红书测试账号。
2. 创建获客任务：平台选"小红书（Beta，需确认）"，勾选风险确认，预算 ≤3 视频。
3. 执行并等待完成，核对候选与证据。
4. 记录证据：任务 ID、视频/评论数、候选截图、验证码/中断时的行为记录。
5. 通过后：`xiaohongshu.prospecting` 由 `beta` → `verified`，并从 `PROSPECTING_BETA_PLATFORMS` 移入默认平台列表（仍需低量灰度一周）。

## 4. 通用规则

- 任何一步触发验证码/风控：立即停止，记录现象，按失败路径处理，不重试绕过。
- 每个能力只执行批准的次数；重复执行需新的批准单。
- 证据统一存档在 `docs/delivery/acceptance-evidence/<日期>-<平台>-<能力>/`。
- 验收未通过时能力保持 `beta/unverified`，并把失败原因写入 `crm-release-status.md`。
