# 自然语言需求驱动的社媒获客设计

**状态：** Draft
**日期：** 2026-09-23

## 1. 目标

把现有“用户填写关键词，系统逐词搜索”的关键词获客，改造成“用户描述想找什么客户，系统识别意图并组合多种获客策略”的需求驱动流程。

目标产品链路：

`输入获客需求 → 意图分析 → 策略组合预览 → 用户确认 → 分策略采集 → 跨策略去重与评分 → 输出潜客和命中依据`

用户不再创建、维护或理解关键词。平台搜索需要的查询表达式属于内部执行计划，由系统生成并保留来源关系。

## 2. 当前实现与问题

当前链路以 `keywords[]` 为核心：

- Web 将文本按空格、逗号和换行拆成关键词。
- `POST /api/prospecting/tasks` 只接受平台、关键词和采集参数。
- `ProspectingTask.keywords` 是任务的主要输入。
- 执行器按关键词循环搜索、抓取评论和计算进度。
- 规则评分和语义评分均把关键词作为主要上下文。
- 候选人只记录一个 `keyword`，同一用户跨关键词出现时主要保留最高分结果。

这会产生四个直接问题：

1. 用户必须自己完成需求分析，输入质量决定结果上限。
2. 单组关键词无法覆盖求助、比较、竞品不满、预算咨询等不同购买信号。
3. 搜索命中和真实购买意图混在一起，容易把同行、讲解者和泛兴趣用户当作潜客。
4. 结果只解释“命中了哪个词”，不能解释“为什么这个人符合用户的获客需求”。

## 3. 产品原则

### 3.1 需求是主对象

任务的唯一用户输入是完整自然语言需求，例如：

> 寻找正在考虑采购私域运营工具的中小企业负责人，优先零售和教育行业，排除同行、代运营服务商和求职者。

系统必须从需求中识别目标客户、问题场景、购买信号、限制条件和排除对象。不能再要求用户补填关键词才能执行。

### 3.2 策略计划可解释、可确认

系统必须在采集前展示意图摘要与策略组合。用户可以启用或关闭策略并调整采集规模，但不编辑内部查询表达式。

### 3.3 多策略共享一份预算

策略数量不能等同于无限扩大采集量。系统先读取账号当日剩余额度，再按优先级为策略分配预算；额度不足时减少低优先级策略的查询和视频数。

### 3.4 结果按需求评分

候选人的最终评分基于原始需求、结构化意图和多条证据。内部搜索表达式只用于召回，不能单独证明购买意图。

### 3.5 本地优先

需求、意图分析、策略计划、执行进度、采集内容和候选人全部存放在 `LOCAL_DATA_DIR` 对应的本地运行环境。调用用户配置的模型服务时，只发送完成意图分析或候选人评分所需的数据。

## 4. MVP 范围

### 包含

- 抖音平台的自然语言需求输入。
- 结构化意图识别。
- 七类预定义策略的选择和组合。
- 策略计划预览、启停和确认。
- 按策略预算执行现有搜索与评论采集能力。
- 跨策略候选人合并、证据保留和需求相关度评分。
- 结果页展示命中策略、意图判断和证据。
- 旧关键词任务的数据迁移与只读兼容。

### 不包含

- 新增尚未验证的社媒平台爬虫。
- 让模型自由生成并执行任意工具调用。
- 自动私信、自动评论或自动加好友。
- 长期自主运行和自动扩展采集预算。
- 训练或微调专用意图模型。

## 5. 核心领域模型

### 5.1 ProspectingIntent

意图分析必须返回受 schema 约束的结构，禁止保存未经验证的模型原文作为执行计划。

```ts
type ProspectingIntent = {
  version: 1;
  summary: string;
  offering: string;
  targetAudience: {
    roles: string[];
    industries: string[];
    organizationTypes: string[];
    regions: string[];
  };
  painPoints: string[];
  useCases: string[];
  buyingSignals: string[];
  exclusions: string[];
  ambiguities: string[];
};
```

`ambiguities` 用于提示需求中影响结果的缺失信息。MVP 不阻塞用户继续执行，但必须在预览中展示。

### 5.2 ProspectingStrategy

MVP 使用有限策略枚举，不允许模型创造未知策略类型。

| 类型                         | 目标信号                         | 示例                         |
| ---------------------------- | -------------------------------- | ---------------------------- |
| `pain_help`                  | 明确求助或问题表达               | “门店私域一直做不起来怎么办” |
| `solution_comparison`        | 比较方案、工具或服务             | “企微 SCRM 哪家适合小团队”   |
| `competitor_dissatisfaction` | 对现有产品或服务不满             | “某工具太贵且不好用”         |
| `purchase_evaluation`        | 采购、试用、选型和实施咨询       | “准备上系统，应该怎么选”     |
| `price_budget`               | 价格、预算和投入产出询问         | “一套私域系统多少钱”         |
| `role_scenario`              | 目标角色在具体业务场景发声       | “教培校长如何做续费转化”     |
| `trigger_event`              | 新店、扩张、转型、政策等触发事件 | “新开三家门店，需要统一运营” |

```ts
type ProspectingStrategy = {
  id: string;
  type: ProspectingStrategyType;
  title: string;
  rationale: string;
  enabled: boolean;
  priority: 1 | 2 | 3;
  queries: string[];
  negativeSignals: string[];
  budget: {
    maxQueries: number;
    maxVideos: number;
  };
};
```

`queries` 是平台适配器使用的内部搜索表达式。它们只出现在服务端执行计划和诊断日志中，常规 UI 不提供编辑入口。

### 5.3 ProspectingPlan

```ts
type ProspectingPlan = {
  version: 1;
  requirement: string;
  intent: ProspectingIntent;
  strategies: ProspectingStrategy[];
  limits: {
    maxTotalQueries: number;
    maxTotalVideos: number;
    maxCommentsPerVideo: number;
  };
};
```

约束：

- 需求长度为 20–2000 个字符。
- 生成 3–7 个策略，至少 2 个启用。
- 每个策略最多 3 条查询，总查询数最多 12 条。
- 查询去重后才能进入执行器。
- 总视频预算不得超过账号当日剩余额度和现有风控上限。

### 5.4 候选人归因

候选人需要保留跨策略证据：

```ts
type ProspectAttribution = {
  strategyId: string;
  strategyType: ProspectingStrategyType;
  query: string;
  evidenceIds: string[];
};
```

同一用户命中多个策略时，合并为一个候选人，累积归因与证据。最终展示：需求匹配摘要、购买阶段、命中策略、支持证据、排除风险和置信度。

## 6. 意图分析与策略编译

新增独立的 `ProspectingPlanCompiler`，职责仅包括：

1. 校验自然语言需求。
2. 调用组织当前配置的 LLM。
3. 将输出解析为 `ProspectingIntent` 和候选策略。
4. 通过 schema 校验、枚举白名单、长度限制和数量限制规范化输出。
5. 根据账号额度生成最终预算。
6. 返回可确认的 `ProspectingPlan`。

编译器不访问爬虫、不创建候选人、不启动任务，避免意图分析与执行耦合。

### 模型不可用

自然语言意图识别依赖可用的 LLM。模型未配置、超时或返回非法结构时：

- 不自动退回关键词拆分。
- 不创建不可解释的采集任务。
- 返回明确错误和配置入口。
- 保留用户输入，方便配置完成后重试。

这样可以避免产品表面接受自然语言，实际仍按分词结果执行。

### 非可信内容边界

用户需求和社媒内容都按数据处理，不能作为系统指令。模型输入使用固定结构和字段边界；模型输出必须经过 schema 校验，任何工具名、URL 或额外指令均不能进入执行器。

## 7. API 合同

### 7.1 分析需求

`POST /api/prospecting/plan`

请求：

```json
{
  "platform": "douyin",
  "requirement": "寻找正在考虑采购私域运营工具的中小企业负责人，排除同行"
}
```

响应：

```json
{
  "planId": "local-plan-id",
  "plan": {
    "version": 1,
    "requirement": "...",
    "intent": {},
    "strategies": [],
    "limits": {}
  },
  "guard": {
    "videosRemaining": 42,
    "estimatedMinutes": 18
  }
}
```

该接口不创建获客任务，也不触发爬取。分析成功后，服务端将计划保存为当前用户的本地短期 plan draft，并返回 `planId`；draft 默认 24 小时失效，避免客户端篡改内部查询和预算。

当组织配置多个同平台账号时，用户必须在分析前选择一个执行账号。`platformAccountId` 随 plan draft 和任务一起保存，任务执行、额度、验证码冷却及审计均使用该账号，不允许运行时静默切换；仅有一个可用账号时界面自动选中。

### 7.2 创建任务

`POST /api/prospecting/tasks`

请求改为：

```json
{
  "platform": "douyin",
  "planId": "local-plan-id",
  "enabledStrategyIds": ["strategy-1", "strategy-2"],
  "minRelevanceScore": 40
}
```

服务端按组织和用户读取未过期的 plan draft，只允许客户端选择启用策略；需求、意图、内部查询和预算均从服务端快照复制。客户端不能提交未知策略、超额预算或任意执行参数，draft 成功消费后不能再次创建任务。

### 7.3 运行任务

现有 `POST /api/prospecting/tasks/:id/run` 保持不变。worker 从任务快照读取已确认计划，不能在运行中重新调用模型生成另一套策略。

## 8. 数据模型调整

`ProspectingTask` 新增：

- `requirement String`
- `intent Json`
- `strategyPlan Json`
- `planVersion Int`

新增 `ProspectingPlanDraft`：

- `id String`
- `organizationId String`
- `userId String`
- `platform Platform`
- `requirement String`
- `intent Json`
- `strategyPlan Json`
- `expiresAt DateTime`
- `consumedAt DateTime?`

`ProspectCandidate` 新增：

- `attributions Json`
- `buyingStage String?`
- `confidence Int?`
- `riskFlags Json?`

现有 `keywords` 和候选人的 `keyword` 在一次兼容迁移后进入废弃状态：

- 历史任务生成只读的 legacy plan，保留原有查询作为内部执行记录。
- 新 API 不接受 `keywords`。
- 新代码不以 `keyword` 字段进行评分或展示。
- 待历史数据验证完成后，再单独迁移删除废弃列。

不在同一版本中直接删列，以免破坏现有本地数据恢复和历史任务查看。

## 9. 执行流程

1. 用户提交自然语言需求。
2. API 编译并返回意图与策略计划。
3. 用户检查意图摘要，启用或关闭策略并确认。
4. API 创建包含计划快照的 draft 任务。
5. 运行接口获得执行 token 并投递现有 worker。
6. worker 按策略优先级和预算执行查询。
7. 每条原始结果携带 `strategyId + query` 来源。
8. 聚合器按平台用户标识去重，合并多策略证据。
9. 评分器基于需求、意图、证据和 ICP 输出结构化判断。
10. 达到阈值的候选人保存到本地并展示归因。

任务进度从“关键词 2/8”改为“策略 2/5”，展示策略名称、已采集视频数和分析批次，不显示内部查询表达式。

## 10. 评分模型

候选人评分拆成四个稳定维度：

- `audienceFit`：角色、行业、组织类型和地域匹配，0–30。
- `needStrength`：痛点与需求表达强度，0–30。
- `buyingIntent`：比较、预算、采购、试用等购买信号，0–30。
- `evidenceQuality`：证据的新鲜度、明确度和多策略一致性，0–10。

命中排除对象时设置 `riskFlags` 并扣分；明确同行、供应商、求职和纯内容创作者应默认过滤。规则评分提供可预测下限，语义评分基于同一结构补充判断；模型失败时可保存采集进度，但结果必须标记“未完成语义评估”，不能把召回结果直接当作合格潜客。

## 11. Web 交互

创建区域改成一个需求输入框：

- 标题：`描述你想寻找的客户`
- 示例：包含产品、客户、场景和排除对象的完整句子。
- 主按钮：`分析需求`

分析完成后展示：

- 系统理解的目标客户。
- 主要需求和购买信号。
- 排除对象与需求歧义。
- 策略卡片及每项采集预算。
- 总预计视频数、时间和当日额度影响。
- `确认并开始获客` 按钮。

详情页将“关键词”统一替换为“需求”和“命中策略”。候选人卡片展示“为什么推荐”和可回溯证据。

## 12. 状态与错误

- `draft`：计划已确认，尚未运行。
- `running`：按已确认计划采集或评分。
- `completed`：所有可执行策略完成，允许部分策略因额度被裁剪。
- `failed`：计划无可执行策略、账号失效或执行链路整体失败。
- `cancelled`：用户取消。

模型分析失败发生在任务创建前，不产生空任务。单个策略搜索无结果不使整个任务失败；全部策略无结果时任务完成并给出“未召回内容”的明确诊断。

## 13. SDD 验收标准

### 产品验收

- 用户只输入自然语言需求即可生成计划并运行。
- 创建流程中没有关键词输入或关键词校验错误。
- 每个任务至少包含两种启用策略，并能解释每种策略服务于哪个意图。
- 同一候选人跨策略出现时只展示一次，但保留全部有效证据。
- 用户能看到候选人与原始需求的匹配原因。

### 工程验收

- 意图、策略、计划和评分输出都有运行时 schema。
- worker 只消费任务保存的计划快照。
- 总采集量受现有账号额度和任务预算共同限制。
- 模型未配置时不会退化成关键词拆分。
- 新业务数据只写入本地数据边界。
- 旧任务仍可查看，迁移可回滚。

### 质量验收

- 单元、集成和 Web 测试覆盖主流程与失败路径。
- `pnpm lint`、`pnpm typecheck`、相关测试和生产构建通过。
- 使用至少三类需求样本验证策略差异，输出不能是同一套模板换词。
- 人工抽查候选人的策略归因与原始证据一致。

## 14. TDD 测试矩阵

| 层级   | 首要失败用例                       | 完成标准                       |
| ------ | ---------------------------------- | ------------------------------ |
| Schema | 未知策略、空需求、超额查询被拒绝   | 所有边界稳定且错误可读         |
| 编译器 | 同一需求生成多类策略且受预算约束   | 输出可重复校验、无未知字段     |
| API    | 分析不创建任务，确认后保存计划快照 | 权限、配额、非法篡改均被覆盖   |
| 执行器 | 按策略执行并传递来源               | 禁止重新生成计划或绕过预算     |
| 聚合   | 同一用户跨策略合并                 | 证据与归因不丢失               |
| 评分   | 购买信号高于泛兴趣，排除对象被过滤 | 维度分数与总分可解释           |
| Web    | 输入需求、预览策略、确认运行       | 页面不再要求关键词             |
| 迁移   | 历史任务转成 legacy plan           | 历史数据可读且新任务不写旧字段 |
| E2E    | 从需求到候选人归因完整闭环         | 使用本地运行环境可重复通过     |

## 15. 发布门槛

该改造达到上线标准需要同时满足：

1. Spec 中的产品、工程和质量验收全部通过。
2. 真实抖音账号以受控额度完成三类不同需求的手工验收。
3. 无关键词输入残留在新建任务流程、错误信息和常规结果页面。
4. 意图分析失败、验证码、额度不足和模型评分失败都有真实可见状态。
5. 备份恢复后，需求、策略计划、候选人证据和归因保持一致。
